= Workflow and architecture

Two workflows turn operational signals into a diagnosis and a response.
Network investigates OpenShift workload alerts; radio access network (RAN) processing detects and classifies unusual radio performance measurements.
They share supporting services and have linked dashboards, while processing their incidents independently.

== Components and their roles

The diagram summarizes the main paths.
The table also includes supporting components used throughout the lab.

[cols="1,3",options="header"]
|===
|Component |Purpose
|Kafka
|Carries alerts, measurement windows, diagnoses, and outcomes between workflow services on separate event streams.
|Network agent and MCP tools
|The agent investigates alerts and chooses a response. Model Context Protocol (MCP) tools obtain current Kubernetes observations and provide access to automation and ticketing.
|Mantis predictors
|Two CPU-based predictors perform separate tasks: anomaly detection identifies unusual measurement windows; root-cause analysis (RCA) assigns a fault category.
|Llama Stack and MaaS
|Llama Stack connects services to the language model through Models-as-a-Service (MaaS), document retrieval, and the Network workflow's tools. The language model supports Network diagnosis and explains RAN predictions.
|Document ingestion, object storage, and pgvector
|Ingestion prepares Network runbooks and RAN reference documents from object storage for retrieval-augmented generation (RAG). Separate collections in PostgreSQL/pgvector provide relevant passages for each workflow.
|Ansible Automation Platform (AAP)
|Executes existing remediation templates and generated playbooks, and records job status and output. Network uses AAP through MCP; RAN calls the controller API directly.
|Red Hat Ansible Lightspeed and Gitea
|Lightspeed generates a playbook for a selected Network corrective action. The agent validates the playbook, stores it in Gitea, synchronizes the AAP project, and launches its job.
|ServiceNow mock
|Stores Network escalation tickets for human review. RAN does not use this ticketing path.
|Network and RAN dashboards
|Show each workflow's incidents and results and provide chat. Navigation links connect the dashboards; their incident lists remain separate.
|===

== Network: investigate, decide, and respond

A controlled alert enters Kafka and starts the Network agent.
The agent gathers current Kubernetes observations through MCP, retrieves relevant runbooks, and uses the language model to assess the cause and a suitable response.

The decision can follow one of three paths:

* Run an existing AAP template when the assessment and playbook-match guard support it.
* Ask Lightspeed to generate a playbook when a corrective action is established and no existing template fits, then validate and execute it through AAP.
* Escalate to a mock ServiceNow ticket when automation is unsupported or a Lightspeed generation or execution attempt fails.

The workflow publishes its recorded outcome for the Network dashboard, including available job and ticket references.
The lab uses real AAP execution against its example workloads.

== RAN: detect, classify, explain, and respond

A controlled key performance indicator (KPI) window enters Kafka.
The anomaly predictor decides whether it is unusual.
Normal results stop at detection; anomalous results continue to the RCA predictor, which assigns a fault category.

Retrieved RAN documentation and the MaaS language model supply an explanation and recommended fix.
The remediation service maps the predictor's category to an existing AAP template and executes it against the lab's RAN simulator.
The language model does not choose the category or template, and this workflow has no Lightspeed or ServiceNow branch.

The RAN dashboard brings together the prediction, explanation, and automation result for each incident.
