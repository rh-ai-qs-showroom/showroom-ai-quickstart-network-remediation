= Module 4: Follow an intentional escalation
:toc: macro
:toclevels: 1

An on-call engineer needs a useful handoff when the system cannot justify a safe automated change. This scenario supplies incomplete evidence so you can inspect the escalation path and its mock ticket reference.

Estimated time: 10 minutes.

== Learning objectives

* Distinguish successful escalation from successful remediation.
* Identify the mock ServiceNow ticket associated with an incident.
* Identify the evidence a human needs before approving a corrective action.

== Exercise: Trigger and review the handoff

The alert reports intermittent failures without enough evidence for a safe change. The intended response is a mock ServiceNow ticket for human review.

. In the *Network dashboard*, click *Trigger Escalation Demo* once.
+
.Example escalation trigger.
image::network-escalation-trigger.png[Escalation demo trigger result with incident ID topic offset and event,link=self,window=blank]
+
. Record the *Incident ID*, Kafka *Topic* and *Offset*, and the *Event*.
. Expand *Incident Timeline* and find the matching incident. Record its stage, summary, *AAP Job*, and *SNOW* ticket number. The intended outcome is *Escalated* with a mock ticket.
+
.Example escalated incident with a mock ticket number.
image::network-escalation-timeline.png[Escalated incident showing failed remediation and a mock SNOW ticket number,link=self,window=blank]
+
The card can show *Escalated* with `Result: failed`: the result describes corrective automation, while a valid *SNOW* number confirms the handoff. The dashboard has no ticket-detail screen; use the card and agent logs below.
+
. In the application namespace's `agent-service` pod *Logs*, find the workflow using your topic and offset. Compare the available analysis and decision with the ticket-creation result.
+
In the example below, the analysis classified the issue as `Unknown` with confidence `0.5`: the available logs ended before the reported failures, and no affected component or safe change had been established. The ticket response supplies the *SNOW* number on the example card.
+
[source,text]
----
Kafka alert received topic=system-alerts partition=0 offset=25
Root cause analysis: {"failure_type":"Unknown","confidence":0.5,
  "summary":"Intermittent request failures reported by clients; available logs end before the failures. ...", ...}
Decide node invoked
MCP tool create_incident succeeded, response={'success': True, 'ticket_number': 'INC0010327', ...}
Audit record published incident_id=166143b8-6dd6-4d54-bfe0-388ed3bcf99a decision=escalate topic=incident-audit offset=25
----
+
The audit record links the decision to your incident. A failed AAP job or timeout can also lead to escalation.
+
. If automation was attempted, use its recorded job ID to inspect the result in AAP.
. Note why automation could not proceed, any missing evidence, and what a human should investigate next.

=== Verify

* You can connect the incident to its audit decision and explain the reason for escalation.
* You recorded the ticket number when creation succeeded, or identified why it is unavailable.
* You identified the evidence needed for the next investigation step.

=== Troubleshooting

If *SNOW* is `n/a`, inspect the agent logs for a ServiceNow error and check the mock and MCP dependencies. An *Escalated* label alone does not prove ticket creation. If a previously recorded ticket is unavailable, the mock might have restarted and removed its in-memory records.
