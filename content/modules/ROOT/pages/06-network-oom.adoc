= Module 4: Compare remediation approaches
:toc: macro
:toclevels: 1

Compare an existing remediation playbook with a playbook generated by Red Hat Ansible Lightspeed. Both paths use Ansible Automation Platform (AAP) to execute automation against the lab workload.

Estimated time: 15 minutes.

== Learning objectives

* Compare restart and resource-exhaustion responses.
* Follow Lightspeed playbook generation through AAP execution.
* Check the target workload after an automation job.

== Exercise 1: Run the OOM scenario

. In the *Network dashboard*, click *Trigger OOM Demo* once under *Demo Mode*.
. Record the new *Incident ID* and *Target*. The controlled alert describes an `OOMKilled` condition, an exceeded memory limit, and restart history.
. Expand *Incident Timeline* and wait for the card with this incident ID. Review its summary, *AAP Job*, and *SNOW* fields.
. Compare the selected action with the CrashLoop run. An `OOMKilled` assessment can select `scale-up-workers`, subject to sufficient confidence and the playbook-match guard. Use the action reported for your incident if it differs.
. Open AAP from your service details. Under *Automation Execution → Jobs*, find the exact job ID from the incident. Review its template, status, and output. The template name can include an environment-specific prefix.
. In the *OpenShift Console*, select `{edge_namespace}` and open *Workloads → Deployments → edge-nginx*. Check the deployment's replicas, container memory settings, and pod readiness after the job. Compare these with the action shown in the job output.

The bundled `scale-up-workers` playbook increases nginx capacity and restarts its pods. Its default targets are at least three replicas, a `512Mi` memory limit, and a `256Mi` memory request. Review the job's actual parameters when checking the result.

=== Verify

* You can explain how the OOM response differs from the CrashLoop restart.
* The incident's AAP job ID matches the executed job.
* A successful OOM job is followed by the expected deployment settings and ready pods. If the workflow escalates, preserve that outcome for the next module.

== Exercise 2: Generate a response with Lightspeed

. Return to *Demo Mode* and click *Trigger Lightspeed Demo* once. Record the new *Incident ID* and *Target*.
. Review the alert message. It describes DNS resolution failures that persist across restarts. The button publishes a controlled alert; it does not change cluster DNS.
. Wait for the matching *Incident Timeline* card. In the application project's `agent-service` pod *Logs*, find the workflow for this incident and inspect its selected response. When the analysis selects a corrective action that needs a generated playbook, the workflow invokes Lightspeed.
. For a Lightspeed run, follow the available log entries through generation and validation. The agent asks Lightspeed to implement the selected action, validates the returned playbook, commits it to Gitea, synchronizes the AAP project, and creates or updates an AAP job template before launching the job.
. Open the exact *AAP Job* from the incident in AAP. Note the project and playbook path on its job template, then review the job parameters, status, and output. Generated names and playbook content vary between runs.
. In the *OpenShift Console*, inspect the resource named by the selected action and job output. Check whether the intended change occurred and whether the affected workload is ready. If the target or expected change is unclear, ask the facilitator to help locate it before drawing a conclusion.

[NOTE]
====
The scenario does not guarantee a generated playbook. The analysis can select an existing matching template or escalate when it cannot establish a safe corrective action. Record the actual result. A generated playbook that fails validation is not launched; generation and execution failures lead to escalation.
====

=== Verify

* You can distinguish selecting an existing playbook from generating one with Lightspeed.
* For a generated response, you can locate its playbook and matching AAP job, or identify the stage that prevented execution.
* You checked the target after execution, or identified why the workflow escalated.

== Troubleshooting

If no incident card appears, revisit xref:04-readiness.adoc[application readiness]. If Lightspeed generation, validation, project synchronization, or AAP execution fails, retain the incident ID and the reported error for the facilitator. Do not repeatedly trigger a scenario to obtain a preferred result.

Do not use *Reset Lightspeed Demo* to reset these exercises. That button restores CPU settings for a different scenario.

Continue to xref:07-network-escalation.adoc[follow an intentional escalation].
