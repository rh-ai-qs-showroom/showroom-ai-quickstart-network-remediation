= Module 2: Follow the Network happy path
:toc: macro
:toclevels: 1

You are the on-call engineer reviewing a proposed response to a stalled nginx worker. Follow one incident from its demo alert to an Ansible Automation Platform (AAP) job. The intended happy path selects an existing restart playbook and restarts the lab's nginx deployment.

Estimated time: 15 minutes.

== Learning objectives

* Correlate a demo alert, workflow execution, and dashboard outcome.
* Explain how Kubernetes observations and retrieved runbooks inform LLM analysis.
* Distinguish a guarded automation decision from proof of workload recovery.

== Network workflow

Confidence and playbook-match checks guide the response decision:

[mermaid,width=100%]
....
flowchart TB
  alert["Workload alert"] --> kafka["Kafka"]
  kafka --> investigate["Investigate Kubernetes<br/>through MCP tools"]
  investigate --> retrieval["Retrieve relevant runbooks"]
  retrieval --> diagnosis["LLM diagnosis"]
  diagnosis --> decision{"Response decision"}
  decision -->|Matching playbook| job["Run AAP job"]
  decision -->|New corrective action| generate["Lightspeed generation,<br/>validation and publication"]
  generate -->|Ready to execute| job
  decision -->|Human investigation needed| escalate["ServiceNow escalation"]
  generate -->|Failure| escalate
  job -->|Failure| escalate
  job -->|Success| audit["Record outcome in Kafka"]
  escalate --> audit
  audit --> dashboard["Show outcome in<br/>Network dashboard"]
....

Generated playbooks are stored in Gitea and synchronized with the AAP project before execution.
ServiceNow tickets use the lab's mock integration.

== Conventions for the Network exercises

* Demo buttons publish controlled alerts; they do not create the reported pod failure. AAP jobs make real changes to the lab workloads.
* Use your own incident ID and input topic/offset to follow each run. The audit offset belongs to the output topic and can differ.
* Examples are shortened. IDs, model decisions, and outcomes can vary; record the actual result and any unavailable evidence.
* Trigger each scenario once and wait for its outcome before starting another. If no card appears, revisit xref:03-environment.adoc[application readiness].

== Exercise 1: Trigger and identify an incident

The alert describes a stalled nginx worker. The intended response uses `restart-nginx` to roll out `edge-nginx`.

. Open the *Network dashboard* and locate *Demo Mode*.
. Click *Trigger CrashLoop Demo* once. Record the returned *Incident ID*, *Topic*, *Offset*, *Target*, and *Event* before triggering another scenario.
+
.Example CrashLoop trigger result.
image::network-crashloop-trigger.png[CrashLoop demo trigger result with incident ID topic offset target and event,link=self,window=blank]
+
. Read the event and note the reported condition and proposed restart.
. In *Incident Timeline*, click *Expand*. Wait for the card with your incident ID. Record its stage, summary, *AAP Job*, and *SNOW* values. Processing and dashboard refresh are asynchronous.

.Example completed CrashLoop incident. Its AAP job ID identifies the execution to inspect.
image::network-crashloop-timeline.png[CrashLoop incident timeline showing incident ID status and AAP job ID,link=self,window=blank]

[IMPORTANT]
====
The timeline shows completed audit records, rather than a live sequence of every workflow node.
====

=== Verify

* The trigger result identifies the scenario and Kafka offset.
* A matching incident card appears, or you have recorded that it is still missing and investigated the dependency health.
* You have captured the actual outcome, including any escalation.

== Exercise 2: Follow the decision and restart

. Open the *OpenShift Console*. In the application namespace identified in your lab details, open *Workloads → Pods*, select the `agent-service` pod, and open *Logs*.
. Find the workflow invocation with the topic and offset you recorded. Locate the completion message containing your incident ID. Inspect the investigation entries between them. Log detail depends on the deployed log level; record missing details as unavailable.
+
In the example below, the agent requested pod logs, deployment information, and a pod specification through MCP tools. The investigation summary reports that pod logs were available; `RAG retrieval node invoked` shows that retrieval started, but does not by itself show what it returned.
+
[source,text]
----
Kafka alert received topic=system-alerts partition=0 offset=22
Investigate node invoked
MCP tool invoke: get_pod_logs ...
MCP tool invoke: get_deployment ...
MCP tool invoke: get_pod_spec ...
Investigate finished: events=0 errors=0 log_results=0 has_pod_logs=True
RAG retrieval node invoked
----
+
. Continue to the analysis, decision, and job entries. In this example, the assessment describes a transient failure, the guard accepts `restart-nginx`, and job 80 completes. Compare those entries with your own incident.
+
[source,text]
----
Root cause analysis: {"failure_type":"CrashLoopBackOff",
  "summary":"nginx pod crash looping due to transient failure", ...}
Playbook guard verdict for restart-nginx: MATCH
MCP tool launch_job succeeded, response={'success': True, 'job_id': 80, ... 'status': 'pending', ...}
MCP tool get_job_status succeeded, response={'success': True, 'job_id': 80, 'status': 'successful', ...}
Audit record published incident_id=928ab50e-c6c7-4490-95e8-36b5f3098fbd decision=remediate topic=incident-audit offset=22
----
+
The audit record links the decision to the incident card.
+
. Return to the matching timeline card. Compare its summary and artifacts with the available logs. If a job ran, record its ID and result. A successful path can display *Auto-Remediated* or *Remediated*, depending on whether a ticket was also recorded.
. If a job ran, find its ID in the *AAP console* and inspect its template, target variables, status, and output. For a restart, confirm that it targets `edge-nginx` in `{edge_namespace}`. If no job ran, record the outcome and continue to the next module.
. After a restart job, open *Workloads → Deployments → edge-nginx* in `{edge_namespace}`. Compare its rollout and pod readiness with the job output.

=== Verify

* You can connect the incident ID and offset to an audit outcome.
* You can explain why a template match is checked before execution.
* For a successful restart, the matching AAP job completes and the target deployment has a new rollout with ready pods.

=== Troubleshooting

If no card appears, check Kafka and agent health using xref:03-environment.adoc[application readiness]. If the guard rejects the restart, inspect the outcome and ticket instead of assuming the system is broken. For a failed AAP job, inspect its task output and record the job ID and error.

Continue to xref:06-network-oom.adoc[compare OOM remediation and Lightspeed playbook generation].
